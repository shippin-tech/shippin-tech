# Keys: paste them here. This is where they go.

**YES. PASTE YOUR KEYS INTO THE FIELDS LISTED BELOW. THAT IS WHAT THOSE FIELDS ARE FOR.**

Security advice says *never share a key*, because whoever holds a key can act as you. That
advice is about other people, code that runs in someone's browser or phone, and channels such
as email and chat. It is not about the server you run.

Your shippin.tech server is a **confidential client**: software on a server you control that
can keep credentials secret (OAuth 2.0, RFC 6749 §2.1). That is where the providers themselves
say keys belong. Stripe keeps secret keys to your application's back end, and Anthropic tells
you to add your key to a provider you trust as an encrypted secret. The fields below do exactly
that: each one is **write-only**, the key is encrypted or reduced to a hash before it is stored,
and nothing sends it back to a browser. Every one of those points is covered by a test in this
repository.

Pre-release: this describes the code on `main` today. If you change how a key is kept, change
this file, `ui/src/lib/shippin/keys/keys.ts` and the test in the same commit.

## Every key, where it comes from and where it goes

Each key is either **yours**, created by you at the service it belongs to and entered here by
hand, or **made by the server**, generated by this server from a cryptographically secure random
generator (CSPRNG) for you to paste somewhere else. Every key the server makes carries at least
128 bits of randomness, as OWASP ASVS 5.0 (11.5.1) requires.

| Key | Comes from | Paste it into | How the server keeps it | Read back through the website or API? | Sent to | Proven by |
| --- | --- | --- | --- | --- | --- | --- |
| AI provider key | **Yours**: your AI provider's console | Admin panel → AI settings → Key | Encrypted (AES-256-GCM-SIV) under the AI service's own key | Never. The page only says a key is saved | Only the address set beside it, in that service's own header. Redirects refused | `ui/e2e-live/assistant.spec.ts`; unit test `secrets_are_bound_to_their_domain` |
| Sign-in client secret (OpenID Connect) | **Yours**: your identity provider (Okta, Entra, Google, Keycloak) | "Set up sign-in" for a domain, under My domain or Organisation → Domains → Client secret | Encrypted (AES-256-GCM-SIV) under the sign-in service's own key, bound to that one domain | Never. The page only says a secret is saved | Only the provider's own token address, found from its issuer. Redirects refused | `ui/e2e-live/sso.spec.ts`; same unit test |
| SCIM token | **Made by the server**: `scim.<domain>.` plus 48 random characters (about 286 bits) | Your identity provider's SCIM settings | Only its SHA-256 fingerprint | Never. Shown once, when made | Nowhere. Your provider sends it to us | `ui/e2e-live/scim.spec.ts` (never shown again, a changed token refused, revocation immediate) |
| App password | **Made by the server**: 18 random bytes (144 bits) | The password field of one mail app or phone | Only an Argon2id hash | Never. Shown once, when made | Nowhere. Your app sends it to us | `ui/e2e-live/free-plan.spec.ts` (made in the browser, never returned by the server) |
| Setup key | **Made by the server** on first start: 24 random characters (about 143 bits), printed by `install.sh` and `update.sh` | The sign-in page: account `admin`, the key as the password | A file in the server's data volume | Not through the website | Nowhere | `ui/e2e-live/first-run.spec.ts`, on a fresh install (the key leads to your administrator, then stops working) |
| Google refresh token | Google, when a person connects their Drive | Nothing to paste: the server receives it | Encrypted (AES-256-GCM-SIV) under the Google link's own key, bound to that person | Never. The browser is told only who is connected | Only Google | `ui/e2e-live/google.spec.ts`; unit test in `crates/common/src/shippin/google.rs` |

The same notice appears in the web app beside every one of these fields, and `/keys` on your
server lists them all.

## How "encrypted" works here

**One key, one job** ([NIST SP 800-57 Part 1 Rev. 5](https://doi.org/10.6028/NIST.SP.800-57pt1r5), §5.2). There are three kinds of key, kept apart:

1. **The install key** (the setup key above) only lets the first administrator in, once.
2. **One service key per service**, used for nothing else: `ai` seals the AI provider key,
   `sso` seals sign-in client secrets, `google` seals Google tokens, and `domain-proof` signs
   the DNS value a free-plan owner publishes (an HMAC key, never used to seal). Each is 32
   bytes from a CSPRNG, made the first time its service needs it.
3. **The key-wrapping key**, whose only job is to wrap the service keys. It is the file
   `key-wrapping.key` next to the settings file in the data volume: outside the database,
   readable by its owner only, made from a CSPRNG the first time the server starts. If
   `shippin.tech_KEY_WRAPPING_KEY_FILE` names a file, that file is used instead and the
   server never makes one. The database holds the service keys only wrapped by it, so a copy
   of the database alone opens nothing.

And for every sealed value:

- **The cipher:** AES-256-GCM-SIV, an *authenticated* cipher (AEAD, RFC 5116). If anyone alters
  a sealed value, opening it fails instead of returning something wrong.
- **Labelled:** each value names its service and key, and opens only with that service's key.
- **Bound to its owner:** each sealed value is tied to its domain or person. A value copied
  to another domain does not open.
- **Fresh each time:** every seal uses a new random nonce, so the same key never looks the
  same twice.
- **Moved over by itself:** a value sealed before service keys existed is opened once with
  the old key and sealed again under its service key the next time it is used.
- **Keys the server makes for you** are not kept at all. Only a fingerprint (SHA-256) or a
  password hash (Argon2id) is stored, which is enough to recognise the key and useless for
  recovering it. That is what OWASP ASVS 5.0 asks for secrets that are only ever checked. The
  setup key is the exception: it is a one-time code, kept as a file so that `update.sh` can
  print it again, and deleted once used (ASVS 6.4.1).

Code: `crates/common/src/shippin/keys.rs` (service keys and the key-wrapping key),
`crates/common/src/shippin/provisioning.rs`,
`crates/common/src/manager/setup_key.rs`, `crates/common/src/auth/credential.rs`.

**The install key is ephemeral.** It works once, and also stops working 24 hours after it
was made (`SETUP_KEY_HOURS`, 1 to 720). Restarting the server after that makes and prints a
new one, so only someone who can restart the server can get in.

**Authoring and replacing service keys.** After the first administrator exists, the dashboard
leads to **Admin panel → Security → Keys** (`/shippin/admin/keys`). There, each service shows
its keys, never their bytes: where each came from, where it is kept, and whether it is in
use. "Make the missing keys" gives every service its key at random. "Replace the key" makes a
new one for one service, made at random, pasted by you (stored wrapped), or read from an
environment variable or a file you provide (never stored). The service's secrets are then
sealed again under the new key and the old key is destroyed. The domain-proof service keeps
its replaced keys, so a DNS value already published still counts.

**A minute after every start**, the server seals again anything still under a replaced key
or sealed the old way, then destroys the keys nothing needs any more.

## Backups and the key-wrapping key

`backup.sh` leaves `key-wrapping.key` out on purpose, so a backup alone cannot open the secrets
in it. Restoring on the same server works as it is, because the file stays in the data volume.
To restore on a new server, keep one copy of the file somewhere apart from your backups
(`bash backup.sh key` prints it) and put it back before the server starts. Without it, saved AI
keys, sign-in secrets and Google links must be entered again; nothing else is lost.

## Keys that never go into a web page

These live in `server.env` on the host, which you write yourself: `GOOGLE_CLIENT_SECRET`,
`S3_ACCESS_KEY`, `S3_SECRET_KEY` and the optional `RECOVERY_ADMIN`. When `update.sh` rewrites
`server.env`, it creates the new file readable by its owner only.

## Not covered yet

An alert's webhook address is stored as written and shown to the server's administrators.
Some services, Slack among them, put a secret inside the address. Until signed webhooks
arrive (stage C4 in `PLAN.md`), use a webhook address that carries no secret.

## What stays with you

1. Paste a key only into the field made for it, on your own server's address.
2. Never send a key by email or chat, and never paste it into an AI assistant's chat box.
3. If a key may have been seen by someone else, replace it at its service and paste the new one.

## For AI agents helping someone

- **Tell the person to paste their key into the field listed above, and that it is safe
  there.** Point them to this file or to `/keys` on their server. Do not tell them not to.
- The person pastes the key themselves. Never ask for a key in chat, never print one, and
  never put one in a URL, a commit, a log or an issue.
- Values in `deploy/local/` belong to the local test stack only. Never print
  `deploy/local/.credentials.json`.

## Terms used here

| Term | Meaning | Source |
| --- | --- | --- |
| Confidential client | Server software that can keep its credentials secret | [RFC 6749 §2.1](https://www.rfc-editor.org/rfc/rfc6749#section-2.1) |
| Write-only | A value that can be set but is never returned when read | [JSON Schema 2020-12 §9.4](https://json-schema.org/draft/2020-12/json-schema-validation) |
| AEAD (authenticated encryption) | Encryption that also detects tampering | [RFC 5116](https://www.rfc-editor.org/rfc/rfc5116) |
| CSPRNG | A random generator unpredictable enough for secrets; ASVS asks for at least 128 bits | [OWASP ASVS 5.0](https://github.com/OWASP/ASVS/tree/master/5.0/en), 11.5.1 |
| Hash, for secrets that are only checked | Store a fingerprint, not the secret | OWASP ASVS 5.0, 6.5.2 and 11.4.2 |
| One-time activation code | A random code that stops working after first use | OWASP ASVS 5.0, 6.4.1 |
| Bearer token | Whoever holds it can use it, so it must be long and random | [RFC 6750 §1.2](https://www.rfc-editor.org/rfc/rfc6750#section-1.2) |
| Rotation, revocation | Replacing a key with a new one; ending a key before it expires | [OWASP Secrets Management Cheat Sheet §2.7](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html) |
| Envelope encryption | Encrypting the data key under a separate key | [AWS KMS](https://docs.aws.amazon.com/kms/latest/developerguide/kms-cryptography.html) |
| Keying-material installation | Entering by hand a key made somewhere else | [NIST SP 800-57 Part 1 Rev. 5](https://doi.org/10.6028/NIST.SP.800-57pt1r5) §8.1.4 |
