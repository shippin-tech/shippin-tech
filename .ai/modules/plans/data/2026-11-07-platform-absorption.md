## Source-to-destination ownership map

The destinations below are proposed owners to validate in packet 1; they are not claims that these files already exist. Keep the Go module boundary intact where practical, with import paths and Go `internal` rules evaluated before choosing a nesting path. A single repository can contain separate Rust and Go processes; absorption does not imply rewriting the control plane in Rust or placing infrastructure authority in the mail engine.

| --- | --- | --- |

Preserve HTTP/API and database compatibility. |
| `cmd/shippin-hostd`, `internal/hostd`, `agent/` | Host agent and separate diagnostic | Same platform module and a separately versioned host-agent/diagnostic build; preserve enrollment, credential and rollback boundaries. |

| `config`, `install`, `deploy`, `scripts`, Dockerfiles, Compose | Platform configuration, installation, upgrades and operational tooling | Proposed `platform/`-scoped configuration and deploy assets, reconciled with destination `deploy/` and images; do not overwrite the Rust engine deployment or site-specific values. |

The existing Svelte portal already manages the mail engine and has its own login and sessions. The Go console has a different auth/tenant model and `/v1` API. Define an explicit integration and identity mapping; do not merge tenant IDs, session cookies, or admin permissions by matching names. The existing `ui/src/lib/adapter` owns transport, catalog components render without fetching, and SvelteKit remains the sole intended UI. Preserve provider-specific Incus/Proxmox implementations, database migration ordering, durable jobs, dispatch claims, review and audit boundaries. Do not equate copied files or mocked responses with live capability.

3. **Adopt and build the Go platform baseline.** Transfer the reviewed, authorized module files with provenance and required notices into its agreed destination, preserving tests, SQL migrations, API specification, hostd and diagnostics. Integrate source contribution checks and API validation into destination CI. **Proof:** clean-checkout Go and web-contract checks, migration ordering, negative-path tests, build of console and hostd, dependency and secret scans. 4. **Connect processes and secure identity.** Provide configured service discovery/proxying, compatible authentication and explicit authorization/tenant mapping, lifecycle health and clear failure states. 7. **One application and cutover.** Package the Go platform, Rust mail engine and Svelte UI into a documented topology with distinct data stores and configuration where required. Deprecate the source panel only after parity and actual integration evidence, then reconcile duplicate documents and contexts with provenance retained. **Proof:** clean install and upgrade, old routes, identity flow, mail and platform journeys, tenant isolation, failure recovery and rollback all pass; the source ledger has a disposition and recorded proof for every tracked path and feature.
